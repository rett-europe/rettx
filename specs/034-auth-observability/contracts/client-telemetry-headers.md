# Contract: Client-Telemetry Request Headers

**Spec**: [`034-auth-observability`](../spec.md) · **Status**: Draft · **Owner**: rettX control plane
**Producers**: `rettxweb`, `rettxadmin` (every API request) · **Consumer**: `rettxapi` (reads + records on telemetry)

This contract defines the request headers that every rettX **client** attaches to **every**
API call so that server-side telemetry (especially auth failures) is **attributable** and can
be **correlated** with the originating client's own telemetry. It is intentionally tiny and
additive; it changes no response shape and carries **no secrets and no PHI**.

## Headers

| Header | Required | Example | Meaning |
|---|---|---|---|
| `X-Rettx-App-Version` | Yes | `1.0.10` | The client build's user-facing version (`versionName` for the native app; the web build version for the PWA/admin). Lets telemetry attribute a failure burst to a specific release. |
| `X-Rettx-Correlation-Id` | Yes | `c1a2b3d4-e5f6-4789-abcd-0123456789ab` | An **opaque, non-identifying** per-install/per-session id generated by the client. Joins a server-side event to the client's own telemetry for the same session. MUST NOT encode a user id, email, device id, or any PII. |
| `X-Rettx-Client` | Optional | `caregiver-native` \| `caregiver-pwa` \| `admin` | Which client surface issued the request. Helps disambiguate senders. If omitted, the server MAY infer from `User-Agent`. |

### Value rules

- `X-Rettx-App-Version` — the exact released version string; for the native app this is the
  `versionName` (e.g. `1.0.10`), NOT the `versionCode`.
- `X-Rettx-Correlation-Id` — a random UUIDv4 (or equivalent opaque token). Generate once per
  install (persist) or per session; keep it stable across the requests of one app run so a
  burst shares one id. **Never** derive it from user identity.
- All values are ASCII, `<= 128` chars. Missing/oversized values are tolerated by the server
  (treated as absent) and never cause a request to fail.

## Producer requirements (rettxweb, rettxadmin)

1. Attach all required headers to **every** outbound API request via the HTTP interceptor,
   **independently of the Auth0 `httpInterceptor.allowedList`** (these headers ship even on a
   request that — erroneously — carries no bearer token; that is precisely the case we need to
   observe).
2. The correlation id MUST match the `correlationId` the client uses in its **own** App
   Insights telemetry, so client and server rows join.
3. Attaching these headers MUST be best-effort and MUST NEVER block or fail a request.

## Consumer requirements (rettxapi)

1. Read `X-Rettx-App-Version` → telemetry dimension `client.app_version`; read
   `X-Rettx-Correlation-Id` → `client.correlation_id`; read `X-Rettx-Client` (if present) →
   `client.surface`.
2. Record these dimensions on **auth-failure** telemetry (and, where cheap, on general
   request telemetry) per spec 034 FR-003.
3. Treat all three as **untrusted, non-authoritative** context: they are for diagnostics only
   and MUST NEVER influence authentication, authorization, or any security decision.
4. Absent/malformed headers → record the dimension as empty; never error.

## Non-goals

- Not an auth mechanism, not a CSRF token, not a device-trust signal.
- Not a user identifier — correlation is session/install scoped and opaque.
- No new response headers are defined by this contract.
